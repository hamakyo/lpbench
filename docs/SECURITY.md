# Security Model

LPBench evaluates code generated by language models. Generated HTML, CSS, and JavaScript must be treated as **untrusted input** even when the benchmark prompt asks for harmless static content.

## Threat model

A generated artifact may accidentally or intentionally contain:

- external network requests
- analytics/tracking scripts
- remote JavaScript or CSS
- attempts to read local resources
- excessive CPU/memory usage
- infinite loops
- navigation away from the preview origin
- unexpected downloads or popups
- code that assumes access to secrets or environment variables

LPBench should not rely on prompt compliance as a security boundary.

## Secret isolation

Provider credentials such as `OPENAI_API_KEY` must be available only to the generation process that needs them.

They must never be:

- embedded in generated files
- exposed to the preview web server
- injected into browser JavaScript
- serialized into `result.json`
- written into screenshots or logs
- copied into GitHub Actions artifacts

Preview/evaluation processes should receive the minimum environment required to run.

## Preview server

Generated content should be evaluated through an isolated local HTTP origin such as:

```text
http://127.0.0.1:<ephemeral-port>
```

Avoid using `file://` for normal benchmark evaluation because browser behavior and permissions differ from HTTP-hosted pages.

The preview server should:

- serve only the current artifact directory
- reject path traversal
- avoid directory access outside the run artifact
- bind to loopback by default
- shut down reliably after evaluation

## Browser evaluation

Playwright should treat the generated page as untrusted.

Where practical, evaluation should:

- block or record external network requests
- capture console errors and page errors
- prevent unexpected navigation from invalidating checks
- use a fresh browser context per run
- use timeouts for page load and interactions
- avoid exposing authenticated browser state

External network use should be recorded as an instruction-compliance signal when the benchmark forbids external assets/libraries.

## GitHub Pages preview

If generated artifacts are later shown inside the LPBench dashboard, do not trust them as part of the dashboard application itself.

Prefer a sandboxed iframe, for example conceptually:

```html
<iframe sandbox="allow-scripts" ...></iframe>
```

Do not grant additional sandbox capabilities unless a benchmark requires them and the risk is understood.

A stronger long-term design may serve generated artifacts from a separate origin.

## Resource limits

Evaluation must eventually enforce practical limits for:

- generation timeout
- preview startup timeout
- page load timeout
- interaction timeout
- Lighthouse timeout
- artifact size

A pathological generated artifact should fail its run rather than stall CI indefinitely.

## Raw provider data

Raw generation metadata may contain fields that are unnecessary for publication. Persist only what is useful for reproducibility and debugging.

Before storing provider responses in Git or Actions artifacts, ensure authentication headers, API keys, request authorization data, or other credentials are absent.

## Dependency policy

The benchmark-generated artifact may be constrained to no external libraries, but LPBench itself may use trusted project dependencies such as Playwright and Lighthouse.

Keep infrastructure dependencies explicit, versioned, and separate from generated-artifact dependencies.

## Principle

Generation credentials and host privileges belong to LPBench infrastructure. They are never capabilities granted to the generated web page.
